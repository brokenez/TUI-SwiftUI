# Поэтапная работа с существующей TUI-библиотекой

**Актуальное уточнение, 13 октября 2026:** [работать в нативном каталоге Xcode](../Documentation/native-catalog-focus-2026-10-13.md). Продолжать SwiftUI-библиотеку и приложение каталога в iOS Simulator. Развитие веб-каталога прекращено; существующие веб-файлы и исторические проверки сохраняются. Компоненты показывать и проверять в нативном приложении.

**Последнее решение, 9 октября 2026:** [исключить системные компоненты Apple](../Documentation/system-components-scope-2026-10-09.md). В реестре остаются 128 исходных наборов, но 16 `system-*` получают статус `excluded`. Довести до приёмки нужно 112 остальных наборов. Системные элементы экранов создаются нативными API iOS 26 напрямую; кастомные TUI-компоненты продолжаем реализовывать на SwiftUI. Figma не изменять. Прежние числа «128 complete» ниже относятся к истории объёма.

**Последнее уточнение пользователя, 8 октября 2026:** [объём прототипов](../Documentation/prototype-acceptance-scope-2026-10-08.md). VoiceOver, увеличенные accessibility-шрифты и прочие дополнительные режимы доступности исключены. Обязательны полная функциональность Figma-компонента, адаптивность содержимого/ширины, обычная типографика, обе темы, специфицированные анимации и реальная работа. Перед изменением компонента сначала прочитать всю доступную спецификацию и схемы, включая зависимости; затем делать компонент. Упоминания расширенной доступности ниже относятся к прежнему плану.

Актуальный порядок задан пользователем 8 октября 2026. Основное применение — интерактивные SwiftUI-прототипы, запускаемые в Xcode Simulator на iOS 26. Все 128 ранее импортированных наборов остаются в реестре; не восстанавливать прежние отметки complete без проверки. Deprecated и явные исторические платформы учитываются отдельно. Новые кандидаты из актуальной Figma требуют подтверждения и не теряются из инвентаризации.

Уточнение пользователя: отдельную библиотеку Deprecated и демонстрации для неё не создавать. Сохранять только исторические ссылки. Доводить актуальные компоненты по группам: Foundations → Buttons → Textfields → Cells → Cards → Navigation → Bottom Sheets → Controls → Feedback → Content. Зависимость из другой группы проверять перед её использованием; порядок групп не разрешает пропускать зависимости или приёмку.

## 1. Инвентаризация

Сохранить существующие metadata, API, ресурсы и доказательства. Свести Components и Legacy, Component Set/Component IDs, всю матрицу, свойства и состояния. Проверить публикацию, Variables и вложенные компоненты; неизвестные поля явно UNVERIFIED. Основной индекс — `docs/inventory.json`, статусы — `docs/component-status.md`.

Текущий результат: 128 сохранённых наборов, 59 реализаций, 2 принятых набора; группировка в 10 разделов. Свежий MCP-снимок Components/Legacy сохранён. 14 кандидатов календаря, 152 не наблюдаемых в текущем page metadata variant ID и недоступный published graph требуют отдельной сверки. Этап не объявлен полностью завершённым.

Критерий выхода: каждому подтверждённому набору назначена группа; публикация/lifecycle, свойства, применимость и зависимости подтверждены либо имеют конкретную запись UNVERIFIED с причиной и источником. Не предполагать отсутствие спецификации по пустому canvas-ответу.

## 2. Спецификации

Использовать уже найденные `Documentation/figma-spec-links.json` и материалы `Documentation/References`, дополнять документы `docs/specifications`. Для каждого компонента читать описание, прямую ссылку, страницы и дочерние разделы, изображения, corner cases и accessibility. Сохранять точный первоисточник и расхождения между версиями. Недоступность — UNVERIFIED, без выдуманных правил.

Начать подробную сверку с Foundations и зависимостей Button, Textfield, Cell. Документы групп уже содержат исходные ссылки, полные свойства и состояние существующих проверок; это индекс, а не утверждение о завершённом извлечении всех спецификаций.

Критерий выхода: для каждой группы есть документ; каждый компонент имеет извлечённые правила с источниками либо конкретную запись UNVERIFIED. Для реализации отдельного компонента его доступную спецификацию и зависимости необходимо прочитать до изменения кода.

## 3. Архитектура

Сохранить текущий Swift Package, публичный модуль `TUIDesignSystem`, токены, ресурсы, нативный каталог и независимый потребитель. Проверить поддержку вариантов, состояний, Day/Night, motion и accessibility. Добавить запрошенное имя поставки `TUI-SwiftUI` совместимым способом; не переименовывать публичные типы ради названия.

Кастомный TUI-компонент не заменяется стандартным SwiftUI-представлением, если меняется дизайн или поведение. Нативные контейнеры и системные взаимодействия iOS 26 использовать там, где этого требует спецификация. Состояние, данные и маршруты принадлежат приложению-потребителю.

Критерий выхода: пакет и каталог собираются; подключение из независимого приложения работает через публичный API; ресурсы доступны. Правила типографики и распространения ресурсов определены явно.

## 4. Foundations и первые три базовых компонента

Сначала проверить существующие цвета, шрифты, отступы, радиусы, размеры, состояния и motion по Foundations. Затем довести до полной приёмки:

Начат [аудит Foundations](../Documentation/References/Foundations/token-audit-2026-10-08.md): чтение 957 токенов во всех импортированных режимах, 23 публичные роли, Day/Night и motion проверены четырьмя тестами в iOS 26 Simulator. Это частичная проверка runtime; пробелы типографики, геометрии и визуальной приёмки перечислены в отчёте.

После разрешённого перезапуска Figma выгрузка MCP работает в проекте. Прочитаны [Typography и особенности iOS](../Documentation/References/Foundations/typography-specification-2026-10-08.md): публичных ролей теперь 31, Dynamic Type сопоставлен по источнику, повторный tracking убран. Пакет и каталог собраны; 23 теста прошли. Полная приёмка line box и решение по версии SF остаются открытыми. Прочитаны также [Color, Size, Shadow и Animation](../Documentation/References/Foundations/color-size-shadow-motion-2026-10-08.md); добавлена Medium-тень, проверка renderer ещё не завершена. Актуальное число complete брать из сгенерированного реестра: изменение общих исходников делает прежние inputHashes неактуальными до содержательной повторной проверки.

Далее исправлен расчёт lineSpacing: используется фактическая высота UIFont, а не его point size. [25 тестов и дополнительная проверка переносов](../Documentation/References/Foundations/typography-specification-2026-10-08.md) подтвердили 32 сочетания восьми Body-ролей, Large/AX5 и явных/автоматических переносов. В исходнике сохраняются неоднозначности Body/XS (таблица 17 pt против 14 pt в иллюстрации) и UI/XS (Caption 1/Caption 2); полного Foundation acceptance пока нет. Следующая зависимая сверка должна проверить прямых потребителей metrics.letterSpacing: правило автоматического интервала относится к композитным системным ролям, а legacy text styles требуют отдельной проверки по источнику. Затем продолжается приёмка Button по полной матрице, включая Night, Dynamic Type, loading, accessibility и motion.

Прямые потребители типографики исправлены и проверены: [45 тестов в Simulator, сборка каталога и сравнение снимков](../Documentation/References/Foundations/typography-consumers-2026-10-08.md). Явные Foundation-роли сохраняют автоматический интервал iOS, свой Dynamic Type и Caps; legacy-стили остаются отдельным вопросом. Далее — спецификация и полная матрица Button.

1. `tui-button`, set `41658:296906`: существующий TUIButton, полная применимая матрица. [Прочитана часть отдельной спецификации и исправлена ширина loading](../Documentation/References/Button/specification-review-2026-10-08.md); 216 runtime-пар проверены. Полная приёмка остаётся открытой: [Масштабирование с адаптивной высотой и fade реализованы и проверены 34 тестами](../Documentation/References/Button/dynamic-type-review-2026-10-08.md); [Night bindings и отступы Construction проверены 14 тестами](../Documentation/References/Button/theme-bindings-review-2026-10-08.md). Далее полная матрица, параметры иконки/цветов/радиуса, VoiceOver и motion; [6 нативных UI-тестов и 14 package-тестов подтверждают исправленные loading label/trait и блокировку действий](../Documentation/References/Button/interaction-accessibility-review-2026-10-08.md). Two labels — отдельный set 51388:47169, [его правила прочитаны отдельно](../Documentation/References/Button/additional-features-review-2026-10-08.md); [полная таблица озвучивания уже прочитана](../Documentation/References/Button/construction-accessibility-review-2026-10-08.md). Большие фреймы дочитывать по частям; дневной лимит MCP не означает отсутствие документации.
2. `tui-textfield`, set `65702:51131`: публичной реализации этого набора пока нет; реализовать заполнение, фокус, ошибки и остальные состояния после чтения источника. Существующий TUISearchInput относится к другому набору и не заменяет его.
3. `tui-cell`, set `41569:290555`: существующий TUICell, варианты контента, ограничения текста и зависимости.

Button и Cell уже реализованы: сверять и исправлять текущий код. Textfield уже проинвентаризирован, его код ещё предстоит создать. Для всех трёх получены свежие MCP definitions Variables и структура по одному варианту. Это частичная инвентаризация: complete требует полной матрицы и всех категорий приёмки.

Актуальное уточнение Button: параметры иконки/цветов/радиуса/ширины и сопоставление 147 вариантов реализованы и проверены. [API review](../Documentation/References/Button/customization-api-review-2026-10-08.md) фиксирует 22 package-теста, 7 Button UI-тестов и успешную отдельную проверку consumer. Снято 270 Day/Night runtime PNG; они ещё требуют сравнения с Figma. Следующие проверки — оставшиеся разделы спецификации, вся визуальная матрица, Glass, тень, fade, VoiceOver и motion. Указанное выше отсутствие параметров относится к предыдущему этапу.

Сохранённая работа CardMedium, HeaderLarge и Skeleton используется повторно как зависимости и доказательства, но не подменяет выбранные базовые компоненты.

## 5. Нативный каталог

Использовать существующее iOS-приложение. Для каждого принятого компонента нужны категории, живой экземпляр из пакета, варианты, состояния, Day/Night и ссылки Figma/спецификации. Демо должны реагировать на системные настройки и давать возможность проверить компонент. При отсутствии реализации это отображается явно.

Веб-каталог сохраняется как дополнение для просмотра нативных рендеров, записей, SwiftUI-кода и спецификаций. Развитие новых возможностей веб-каталога отложено до приёмки компонентов.

## 6. Правила для Codex

Сначала читать AGENTS.md, индекс и доступные публичные API. Собирать экран существующими компонентами и токенами. Не копировать реализации в прототип, не подменять недоступный вариант собственной графикой, не менять API без необходимости. Проверять сборку и реальные действия в iOS Simulator.

Критерий выхода: по файлам репозитория и ссылке Figma отдельный потребитель собирает интерактивный экран без контекста этой переписки и без копирования реализации.

## 7. Приёмка и продолжение

Оставить действующие семь категорий: матрица/API, спецификация, визуальное сравнение, взаимодействия, accessibility, motion, интеграция. Day/Night, состояния, сборка и Simulator входят в доказательства, а не заменяют визуальную приёмку.

Успешную проверку повторять при изменении относящихся к ней входных файлов, выявленной ошибке или незакрытом риске. Проверять общую реализацию один раз, все применимые варианты — пакетно, исключения — отдельно. После первых трёх продолжать по подтверждённым зависимостям до всего объёма. Публикация GitHub согласуется отдельно после готового локального результата.
