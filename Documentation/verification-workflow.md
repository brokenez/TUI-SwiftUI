# Приёмка компонентов TUI

**Актуальный объём от 8 октября 2026:** [решение пользователя](prototype-acceptance-scope-2026-10-08.md) исключает VoiceOver, увеличенные accessibility-шрифты и дополнительные режимы доступности. Проверяются обычная типографика, адаптивность контента/ширины, полная применимая матрица, функции и анимации по спецификации. Поле accessibility сохраняется для совместимости реестра как not-applicable с доказательством явного исключения; не выдавать это за пройденную проверку. До изменения компонента прочитать его доступную спецификацию целиком. Далее описан исходный процесс; требования расширенной доступности и Reduce Motion в нём являются историческими.

Источник истины — Figma Mobile, Foundations и Assets, а не текущий вид каталога. Целевая платформа — iOS 26. Явные варианты iOS 18 хранятся как исторические ссылки, отдельно от применимой матрицы; на симуляторе iOS 26 их поведение не считается проверенным.

## Реестр и статус

`component-verification.json` содержит отдельную запись каждого из 128 наборов: API, параметры всех применимых вариантов, результаты семи проверок, доказательства и контрольные суммы входных файлов. `component-coverage.json` и копия в Resources/Metadata генерируются из него. Каталог читает ту же сгенерированную копию. Статус не назначается вручную.

- `catalogued`: набор найден в Figma, реализации нет.
- `excluded`: системный набор исключён пользователем из переноса; источник и прежний код сохранены. Он не считается complete и не входит в объём реализации. Основание, дата и SHA-256 решения обязательны в `scopeExclusion`; см. [решение от 9 октября](system-components-scope-2026-10-09.md).
- `in-progress`: реализация есть, хотя бы одна обязательная проверка не завершена, есть открытое расхождение либо изменились проверенные входные файлы.
- `blocked`: у реализованного компонента явно зафиксирован блокер проверки.
- `complete`: все семь проверок завершены, все применимые варианты сопоставлены и визуально сверены, входные файлы актуальны, открытых замечаний нет.

`previousStatus` сохраняет прежнюю оценку. Он не даёт права автоматически восстановить `complete`. При переходе на этот процесс 33 прежние отметки complete оставлены в истории; все 52 существующие реализации требуют повторной приёмки. Остальные 76 наборов остаются catalogued.

## Семь проверок

| Поле | Что необходимо подтвердить |
| --- | --- |
| `variantMapping` | Каждый применимый node ID имеет однозначное соответствие публичному Swift API и его параметрам. Имена и значения Figma сохранены в метаданных. Не допускаются молчаливые подмены отсутствующих состояний. |
| `specification` | Прочитана отдельная спецификация: размеры, ресайз, ограничения текста, состояния, состав, кастомизация и исключения. Подпункты и node ID перечислены в отчёте. При отсутствии страницы это фиксируется и проверяется доступный источник, а не предполагаемая спецификация. |
| `visual` | Для каждого варианта есть PNG из Figma и PNG работающего компонента, сопоставленные по variant ID. В отчёте указаны масштаб, устройство, iOS, тема, размер текста, параметры, измеренные расхождения и решение по ним. Дополнительные состояния из спецификации проверены отдельно. |
| `interaction` | Нажатия, выбор, ввод, жесты, disabled, loading и переходы проверены в работающем каталоге. Проверяется действие и итоговое состояние, а не только наличие обработчика в коде. |
| `accessibility` | Исключено из текущего объёма по явному решению пользователя: not-applicable со ссылкой на решение. Предыдущие результаты сохраняются как история. |
| `motion` | Источники длительности и easing установлены. Для продуктовых анимаций измерены переходы и повтор; для системных контейнеров подтверждены стандартные взаимодействия iOS 26 без глобального изменения скорости. Расширенная проверка Reduce Motion исключена. |
| `integration` | Пакет и каталог собираются, релевантные тесты проходят, компонент импортируется и используется через публичный API. Сохранены команды, конфигурация, результаты и проверенные версии файлов. |

Состояния проверки: `pending`, `passed`, `not-applicable`, `failed`, `blocked`. Для `passed` и `not-applicable` обязательны `reviewedAt`, конкретное объяснение в `reason` и сохранённые доказательства. Для `variantMapping`, `visual`, `integration` значение `not-applicable` запрещено. Для остальных неприменимость требует объяснения на основании источника; отсутствие измерений не означает неприменимость.

## Порядок работы над одним набором

1. Открыть запись в `figma-components.json`, полную матрицу в `figma-component-variants.json`, страницу спецификации и связанные компоненты. Обновить контекст из Figma перед изменением реализации. Отдельно перечислить исторические платформы.
2. Заполнить `variantMappings`: ключ — точный применимый variant ID; значение содержит `symbol` публичного компонента и словарь `parameters` с фактическими параметрами API. Проверить все текстовые/boolean свойства экземпляров и дополнительные состояния из спецификации, даже если они не являются отдельными вариантами.
3. Использовать исходные токены. Для legacy-исключений сохранить источник и причину. Найти ассеты через `figma-assets.json`, сохранить исходный экспорт и проверить импорт в скомпилированном приложении.
4. Добавить живые примеры и управление параметрами в каталог. Снять варианты, проверить действия, доступность, изменения размеров, обе темы и анимации, предусмотренные источником. Сохранить сравнения и отчёт в `Documentation/References/<имя компонента>/`.

   Для движения читать спецификацию, `get_motion_context` и доступные сведения `reactions` исходных вариантов и вложенных экземпляров, включая AFTER_TIMEOUT, CHANGE_TO, длительность и easing. Использовать только инструменты чтения MCP и проверенные локальные выгрузки; `use_figma` / Plugin API запрещён пользователем даже для предполагаемого чтения. Недоступные данные оставить UNVERIFIED. Пустой ответ `get_motion_context` сам по себе не подтверждает отсутствие анимации: у Skeleton именно так был пропущен наследуемый цикл. Сопоставлять кривую и длительность с Foundations; проверять оба направления, паузы и повтор. Статические сравнения выполнять с явно остановленной анимацией. Для временных проверок нужна активная сцена приложения: безоконный раннер Swift Package может отрисовать кадр, но не обновлять TimelineView. Проверки расширенной доступности и Reduce Motion исключены текущим решением пользователя.
5. Сохранить результаты сборки/тестов и заполнить проверки доказательствами. Закрыть `openIssues` только после исправления и повторной проверки каждого замечания.
6. Зафиксировать `inputHashes`, сгенерировать обе копии покрытия и проверить их актуальность. Убедиться, что статус complete получен по данным приёмки и соответствует фактически выполненным проверкам.

## Доказательства и актуальность

Каждая запись в массиве `evidence` содержит `path` относительно корня проекта и `sha256` содержимого файла. У визуальных доказательств дополнительно обязательны точный `variantID` и `kind`: `figma-reference` или `runtime-render`. Файлы должны находиться внутри проекта. Удалённый URL или временный путь вне проекта не заменяет сохранённое доказательство. Один файл может содержать несколько вариантов; для каждого нужна отдельная связь с variant ID и описание области в отчёте.

`inputHashes` — словарь относительных путей и SHA-256 проверенной версии. Обязательный минимум: файл реализации, импортированная матрица вариантов и foundations. Вручную дополнительно включаются реальные зависимости: общая типографика, шрифты, использованные компоненты, токены, ассеты и относящиеся к компоненту данные спецификации. После изменения зависимости результаты повторно проверяются; прежние контрольные суммы не обновляются только ради сохранения статуса.

Для вычисления суммы отдельного файла используется `shasum -a 256 <фактический путь>`. В доказательствах указываются реальные файлы, а не демонстрационные значения. PNG из тестовых фикстур валидатора не являются доказательствами соответствия Figma.

Генератор проверяет наличие вариантов, структуру доказательств и контрольные суммы. Он **не оценивает сходство изображений**, правильность озвучивания или плавность движения. Решение passed требует содержательной проверки и отчёта; наличие двух PNG само по себе не подтверждает качество. Полнота списка дополнительных зависимостей и случаев из спецификации также проверяется человеком или агентом при приёмке.

## Воспроизводимые проверки

Из корня проекта:

```sh
python3 Scripts/generate_component_coverage.py
python3 Scripts/generate_component_coverage.py --check
python3 Scripts/verify_live_components.py
python3 -m unittest discover -s Scripts/tests -v
```

Тесты Swift Package запускаются через `PackageTests.xcworkspace`, общую схему `TUIDesignSystemTests`. Это настоящий тестовый target пакета с его ресурсами, а не отдельная копия исходников. Для запуска выбирается доступный симулятор iOS 26. Текущий проверенный destination:

```sh
xcodebuild -workspace PackageTests.xcworkspace \
  -scheme TUIDesignSystemTests \
  -destination 'platform=iOS Simulator,id=6D3F35A1-AC30-4F0E-BDD6-0F912B714E59' \
  -derivedDataPath /private/tmp/tui-package-tests-derived \
  -clonedSourcePackagesDirPath /private/tmp/tui-package-cache \
  -skipPackageUpdates CODE_SIGNING_ALLOWED=NO test
```

Идентификатор симулятора зависит от компьютера. Перед запуском на другом компьютере следует выбрать существующее устройство, не утверждая, что приведённый UUID там доступен. После публичных API-изменений дополнительно собирается standalone-приложение каталога по конфигурации проекта.

Сохранённый результат должен различать: сборку, успешный код завершения тестового запуска, число фактически выполненных тестов и ручные визуальные/интерактивные проверки. Ошибка инфраструктуры не считается успешной проверкой компонента. Все непроверенные пункты остаются pending или имеют явно описанный блокер.
